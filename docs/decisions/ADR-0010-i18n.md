# ADR-0010 — Internationalisation: one message catalogue, five complete locales, graceful fallback

- **Status:** Accepted
- **Date:** 2025-11-23
- **Relates to:** [ADR-0003](ADR-0003-design-system.md)

---

## Context

The baseline ships four locales — `en`, `ru`, `uk`, `vi` — with roughly 310
message keys each, in `plugin/_locales/*/messages.json`. The catalogue is
mostly complete in all four.

The baseline's localisation has several defects:

- **`UIText` computes every string eagerly at class-definition time**
  (`UIText.js:10-124`). Each `chrome.i18n.getMessage` call runs at script
  load, which is ~310 synchronous calls on every popup open, for strings the
  user may never see.
- **`localizeHtmlPage` walks the DOM and replaces text starting with
  `__MSG_`** (`main.js:472-481`). It matches `button`, `option`, `td`, `th`,
  and `.i18n` elements — a brittle whitelist. Any new element type must be
  added to the list or its placeholder text leaks into the UI.
- **Entities are not decoded.** The localisation uses `textContent`, so
  `label_Use_SVG_for_Images` = _"Use &lt;svg&gt; for images"_ renders the
  entity **literally** in the interface.
- The `__MSG_` placeholder convention collides with real user content: a
  chapter title that happens to start with `__MSG_` would be rewritten.

## Decision

We keep `browser.i18n` (it is the right tool — it gives Firefox's locale
plumbing, and the locale files are the format the store expects), but we
fix the four defects above.

### 1. Lazy, memoised message lookup

```ts
export function t(key: MessageKey, substitutions?: string[]): string {
    // memoised per key
}
```

Messages are resolved **on first use**, not at module load. A memoised
lookup is ~100× cheaper than 310 eager calls per popup open, and it means
unused strings cost nothing.

### 2. No DOM placeholder convention

The `__MSG_` placeholder sweep is **removed**. Localisation happens at the
point of use:

```ts
const label = t("chapterCount", [String(count)]);
this.shadowRoot.querySelector(".count").textContent = label;
```

Because the components are Web Components with their own templates, each
component owns its own localisation. A new component cannot forget to
register a string, because the string is referenced in the same file as the
template that uses it.

For **static markup** in the page shell, we keep a small declarative
attribute:

```html
<span data-i18n="chapterCount"></span>
```

and the shell's own render pass fills it. This keeps the HTML readable
without a global sweep over arbitrary DOM.

### 3. Placeholders use `browser.i18n` substitutions, not HTML

`browser.i18n` supports `$1`-style substitutions, so a message with a
variable is a single message with a substitution list — no concatenation, no
HTML injection risk:

```json
"chapterCount": { "message": "$1 of $2 chapters" }
```

Entities are never present in a message, which fixes the `&lt;svg&gt;`
bug at the root.

### 3a. Counts are pluralised by the extension, not by the browser

`browser.i18n` looks up a key and substitutes into it. It does **not** choose
a plural form: the `_one` / `_other` key suffixes that Chrome's own tooling
writes are ignored by Firefox, and the message is returned as-is.

This was measured, not assumed. A throwaway extension was installed in real
Firefox and asked for a key whose catalogue carried a `_one` variant; the
answer was the plural form, every time. `getMessage(key)` with no
substitution list returned the literal word "null" in place of the missing
value, which is a second reason never to call it without arguments.

So the extension does the pluralising itself:

- a counted message is written as **two keys** — `popupChapterCount` and
  `popupChapterCountOne` — and `tCount(key, count)` picks between them;
- the count is passed as the **first** substitution, so the message reads
  `"$1 chapter"` rather than `"chapter: $1"`;
- a locale that does not need a different singular says so by making the two
  messages the same, which is what German, Indonesian and Japanese do.

The plural rule is the one place where the extension's own logic touches the
text, so it is worth being explicit about: it is a binary choice — one or
more than one — and it is not a general plural engine. For a count of
chapters, a count of books, and a count of images, that is the whole of what
is needed.

### 4. Graceful fallback for incomplete locales

The rewrite reworks every user-facing string, so the existing translations
cannot be reused verbatim. Our approach:

- **`en` is the source and is authoritative.** Every key in the new catalogue
  exists in `en`.
- The source of truth for a translation is a hand-written file under
  `tools/locales/<locale>.mjs`, one per locale. The generator reads them and
  writes `src/_locales/<locale>/messages.json`. English is the exception:
  `tools/locales/en.mjs` is deliberately empty, because the English text
  already lives in the generator's `SOURCE` table. A key that appears in
  `en.mjs` would override the source, which is never what you want.
- **A missing key falls back to English.** `browser.i18n` falls back to
  `default_locale` for any key a locale does not define, so a partially
  translated locale shows English for the untranslated strings and the
  translated ones in the user's language. This is strictly better than the
  baseline, where a missing key renders the literal key name.
- **All five shipped locales are complete** — `en`, `de`, `fr`, `id` and `ja`
  each cover every key. The fallback is retained as a safety net for a
  future locale that is not yet finished, not as a description of the
  current state.
- A **catalogue test** (`tests/unit/locales.test.ts`) asserts that every
  locale has exactly the source's key set, that every `$TOKEN$` in a message
  has a matching placeholder declaration, that the placeholders are numbered
  by position so none silently overwrites another, that a locale uses the
  same placeholder tokens as the source, and that every message carries a
  description. A translation gap is therefore a **test failure**, not an
  invisible degradation.
- Translators are invited via `CONTRIBUTING.md`, which documents the message
  format and the fallback behaviour.

### 5. Typography and layout tolerate longer strings

The rewrite's UI is designed for the **longest** supported locale, not the
shortest. German-style verbosity in a 320 px panel is a layout bug, so
buttons use `min-width` with a flexible max, labels wrap rather than
truncate, and the a11y tests run against the longest locale as well as the
default.

## Alternatives considered

| Alternative                                              | Why rejected                                                                                                                                                                                               |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A runtime i18n library (i18next, lingui)**             | ~10–30 KB and a build-time message extraction step, for a product with ~200 strings and five locales. `browser.i18n` already integrates with the store's locale plumbing.                                  |
| **Keep the `__MSG_` sweep but widen the whitelist**      | Still brittle, still collides with user content, still leaks entities.                                                                                                                                     |
| **Hard-code English**                                    | The baseline ships four locales and the community maintains them. Dropping them is a product regression.                                                                                                   |
| **Machine-translate the new catalogue into all locales** | Would ship unreviewed, often wrong translations — worse than an honest English fallback. The catalogue test makes the gap explicit.                                                                        |
| **Use ICU message format for plurals**                   | `browser.i18n` supports only simple substitutions, and Firefox ignores the `_one` / `_other` suffixes that would select a form. The plural choice has to be made in code, from two explicit keys. See §3a. |

## Consequences

**Positive**

- Localisation cost drops from ~310 eager calls per open to a handful of
  memoised lookups.
- The `__MSG_` collision with user content is impossible.
- Entities are decoded correctly.
- A missing translation degrades to English instead of to a raw key.
- Each component owns its strings, so a new component cannot forget them.
- A translation gap is a **test failure** rather than a silent degradation.

**Negative**

- The `data-i18n` attribute requires a render pass for static markup.
- A locale is only as good as its last translator; the catalogue test catches
  a _missing_ key, but not a _bad_ one.
- The plural choice is binary. A language with more than two plural forms —
  Polish, Russian, Arabic — is given the same two strings as every other
  language until the catalogue grows a third key.

**Neutral**

- The message catalogue lives in `src/_locales/`, in the same format Firefox
  expects, so the store packaging is unchanged.
- The hand-written translations live in `tools/locales/`, outside the shipped
  tree. They are build inputs, not runtime code.
