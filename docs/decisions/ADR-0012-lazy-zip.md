# ADR-0012 — Load the ZIP library on demand, behind a lazy facade

- **Status:** Accepted
- **Date:** 2025-11-23
- **Relates to:** [ADR-0002](ADR-0002-parser-contract.md), [ADR-0008](ADR-0008-epub-pipeline.md)

---

## Context

The extension's EPUB writer is a dependency we control (ADR-0008), and it does
its own ZIP writing.

But one of the 434 migrated parsers — `DarkNovelsParser` — needs to **read** a
ZIP: that site's API returns the chapter text as a `.zip` archive. In the
baseline it used the global `zip` namespace from the `zip.js` library, which
the baseline's popup page loaded with a `<script>` tag.

That library is **155 KB minified**. In the baseline it was loaded on *every
popup open*, on every page, whether or not the user was ever going to read a
ZIP — because it was a `<script>` in the popup, not a dependency of the feature
that used it.

The rewrite has two constraints in tension:

- The migrated parsers must keep working **verbatim** (ADR-0002). We do not
  edit 434 files to change an import style, and the codemod that produces them
  is reproducible — hand-edits are lost on the next run.
- The background worker ships the parsers. Adding 155 KB of ZIP library to the
  worker bundle is a real cost for every user, forever, for one parser whose
  own site is, in the baseline's author's words, *"server is down so i am
  unable to test the code"*.

There is also a security consideration: `zip.js` is a third-party library that
parses untrusted archive data. The fewer users who have it, the smaller the
attack surface.

## Decision

We load `zip.js` **on demand**, behind a lazy facade, and keep the global's
shape so the migrated parser needs no change.

### The facade

`src/core/parsers/compat/legacy-zip.ts` exports a `zip` object that is a
`Proxy`. Every property access returns a function that, when called, starts
loading the module (once) and returns a **lazy instance** — itself a `Proxy`.

The lazy instance is **thenable**: awaiting it yields the real `zip.js`
instance. That is what makes the baseline's code work unchanged:

```js
// The baseline's parser:
const reader = new zip.Uint8ArrayReader(bytes);      // lazy proxy
const zipReader = new zip.ZipReader(reader);          // lazy proxy, not awaited
const entries = await zipReader.getEntries();         // resolves to the real thing
```

Two details matter:

- The baseline `await`s the reader but **not** the `ZipReader`. The facade
  handles both: the instance is created as soon as the module has loaded, and
  every method call waits for that.
- `ZipReader` takes a reader as its first argument, so the lazy instance's
  arguments are **unwrapped** (`await Promise.all(args)`) before the real
  constructor sees them. Otherwise the real `ZipReader` would be handed a
  proxy instead of a reader.

### The bundling consequence

`import("@zip.js/zip.js")` is a **dynamic** import, so the bundler emits
`zip.js` as a separate chunk rather than inlining it. The chunk is fetched
the first time a parser actually needs it, and never for the other 433
parsers.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| **Bundle `zip.js` eagerly** | 155 KB added to the worker bundle for one rarely-used parser. The baseline already did this — in the popup, on every open — and it is exactly the kind of waste this revamp exists to remove. |
| **Rewrite `DarkNovelsParser` to import the library directly** | The parser is generated by `tools/migrate-parsers.mjs`; a hand-edit is lost on the next run. A codemod exception for one file is possible but adds a special case to a tool that is meant to stay generic. The facade is the general solution to a general problem: any migrated parser that used a browser global gets a facade. |
| **Implement ZIP reading in-house** | A ZIP reader is a small format, but "small" is doing a lot of work: deflate, ZIP64, data descriptors, and a decade of malformed archives in the wild. `zip.js` is battle-tested. Hand-rolling it is a security risk, not a saving. |
| **Drop the parser** | It is one of the 434 parsers that make the product valuable. Dropping a parser is a product regression, and the site may well be back. |
| **Use the DOM's `DecompressionStream`** | It can do raw deflate, but not the ZIP container format: the central directory, the local headers and the data descriptors would all have to be parsed by hand. That is most of the work anyway. |
| **Load the library eagerly but in a separate chunk** | A separate chunk that is *always* fetched saves nothing. The win comes from the import being conditional, not from the code being split. |

## Consequences

### Positive

- The worker bundle does not carry 155 KB of ZIP library.
- `zip.js` — a third-party parser of untrusted data — is loaded only by users
  who visit the one site that needs it.
- The migrated parser is untouched, so the codemod stays generic and the
  parser count stays at 434.
- The same facade pattern is available for any other browser global a
  migrated parser reaches for.

### Negative

- The facade is **more code than the thing it wraps** — a `Proxy` with a
  thenable contract is subtle, and it is the kind of code that breaks when
  `zip.js` changes its export shape.
- The failure mode is late: if `zip.js` fails to load, the parser fails at
  the moment it reads the archive, not at start-up. The failure message names
  the missing export, which is the only mitigation.
- `Proxy` is not transparent: `instanceof`, `Object.keys` and
  `JSON.stringify` do not behave as they would on a real instance. The
  migrated parser uses none of these, but a future one might.
- `zip.forEach` — used by the baseline in a *commented-out* block — is a
  static method, not an instance method, and is not proxied. It is not
  reachable through the facade today; if it is ever needed, it needs a real
  case in the facade.

### Neutral

- The chunk is emitted by the build and served from the extension's own
  package. Nothing is fetched from a CDN, so there is no remote code
  (ADR-0007).
